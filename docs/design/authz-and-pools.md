# 权限模型与资源池（AuthZ & Pools）

## 问题

企业版的访问控制不是后期补丁，而是数据模型的地基：
谁能登录、谁能往哪个池提任务、哪些池的任务能拿哪些数据集、
谁能注册/管理节点——这些规则必须在 server 动工前就有一张明确的表。

## 角色

| 角色 | 说明 |
|---|---|
| `admin` | 全部权限；首启引导创建的第一个用户即 admin |
| `user` | 普通算法工程师：在授权池内提交/查看/停止自己的任务 |

权限矩阵：

| 操作 | admin | user |
|---|---|---|
| 登录 / 修改自己密码 | ✅ | ✅ |
| 用户 CRUD、角色修改 | ✅ | ❌ |
| access token 签发/撤销 | ✅ | ❌ |
| 注册窗口开关 | ✅ | ❌ |
| 资源池 CRUD、节点 assign | ✅ | ❌ |
| 用户↔池、数据集↔池授权 | ✅ | ❌ |
| 节点"安装引擎"等运维操作 | ✅ | ❌ |
| 数据集上传/删除 | ✅ | ❌ |
| 提交任务 | ✅ | 仅授权池，仅授权数据集 |
| 查看任务/日志 | ✅ 全部 | 自己提交的 + 授权池内公共视图 |
| 停止/抢占任务 | ✅ 任意 | 仅自己的任务（停止；抢占是 admin 专属） |

首版只有两级角色；更细的粒度（团队管理员等）随 Phase 5 团队/配额再加，
角色字段在设计上是可扩展枚举，不写死二元判断。

## 资源池（pool）

- 池是**调度与授权的交叉点**：队列按池分（池内 FIFO），授权按池判。
- **节点↔池多对多**：归属是 server 侧元数据，admin 在 web 划分；
  agent `--pool` 只是初始建议（新池名自动创建，缺省 `default`），
  上报值不影响已有归属。
- **自动创建的新池默认无授权**（仅 admin 可用），防野池裸奔。
- **用户↔池**：user 只能向授权池提交任务；admin 不受限。
- **数据集↔池**：任务引用的数据集必须授权给目标池；产物数据集
  自动归属任务所在池（可事后由 admin 调整授权）。
- 池不做资源预留；多池共享节点时靠排队消化，不存在超额分配。

## 节点注册与凭证

两种注册模式（细节见 server-agent-protocol.md）：

1. **token 模式（默认）**：access token 由 admin 签发，字段：
   label、有效期（可选）、 revoked 标记；agent `--token` 携带。
2. **注册窗口模式**：admin 开 toggle，窗口期 Hello 免 token；
   手动关闭恢复白名单。

共同规则：

- 注册成功即下发节点凭证（随 Welcome），agent 存身份文件（0600）；
  之后一切连接凭证认证，与注册模式无关。
- access token 撤销**不影响**已注册节点（session_token 已分离）；
  要踢节点用"吊销节点"（server 删除/禁用 node 记录，拒绝其后续握手）。
- session_token 支持轮换：server 可在任意消息中下发新值，agent 即换。

## 会话与密码

- 密码 argon2id 哈希；登录发会话 token（httpOnly cookie 或 bearer，
  web/API 同一套）。
- 会话有效期可配（默认 12h），登出即失效；admin 可强制下线任意用户。

## 不采用

- 消息层用户级鉴权（协议面只有节点凭证，用户概念止于 server）。
- LDAP/OIDC 对接（首版内置用户系统足够；接口设计上预留外部 IdP 位，
  私有部署客户真需要时再加）。
- 池级资源配额预留（Phase 5 的配额是计量与排队公平性，不是预留）。
