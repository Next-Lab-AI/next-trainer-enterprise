# 计量与计费（Metering & Billing）

## 问题

企业版计费的实际目的（按 SWAT 结论）：

1. **衡量算力需求**——排队深度/时长曲线回答"要不要加卡"，
   比工程师拍脑袋有说服力；
2. **搞清楚算法工程师在干啥**——谁在用、跑什么任务、
   卡的真实利用率（很多企业的真相是分配率 90%、利用率 20%）；
3. **部门间结算（chargeback/showback）**——内部互相 bill，
   计价规则各家不同，平台只出原始用量。

不是面向公众的算力售卖，无计费合规压力；私有部署下 agent 自报数据可信。

## 分层设计

```
agent 采样/事件  →  server 事件流落库  →  用量聚合（meter）  →  计价器（pricing，可替换）
```

**meter 与 pricing 严格分离**：meter 只忠实记录原始用量；
pricing 是策略层（费率表按 GPU 型号/时段/部门配置），
换掉不影响历史数据重算。

## Meter：原始用量流水

粒度：`(user, pool, job_id, job_type, node, gpu_index, gpu_model, start, end, gpu_seconds)`。

- **任务事件流**：job.start / job.end / job.failed / job.preempted
  全部落事件表；用量是从事件流算出的派生物。事件帧携带 GPU 分配，
  "哪张卡跑了多久"从第一天就是必备字段。
- **时间不依赖节点时钟**：跨时区部署（中/美 GPU 共存）合法，
  start/end 以 server 收到事件的时间落库，agent 附 elapsed 相对时长供校验。
- **GPU 采样**：agent 按 gpu_index 逐卡周期性采集（利用率、显存、功率，
  字段厂商中性），有界内存缓冲 → 批量上报 → server 写时序库
  （VictoriaMetrics / InfluxDB 任选，可插拔）；断网溢出丢弃并记 gap。
- **空闲 vs 占用分开算**：分配了没跑满 ≠ 实际算掉，
  两组指标都出（这通常是内部结算最先吵的点，先把数据摆出来）。

## Pricing：可替换计价器

- 首版内置一个简单计价器：费率表 `rate[gpu_model] × gpu_seconds`。
- 计价器是 interface/aspect，企业可换成自己的实现
  （或直接只用量数据，走他们自己的财务流程）。
- **失败/抢占怎么算钱**做成计价规则配置项，不写死。

## 输出

- **Dashboard**（server web）：
  - 按人/团队：GPU 时长、任务数、排队时长
  - 任务类型分布（训练/推理/打标/调参/占着卡的 Jupyter）
  - 卡利用率 vs 分配率
  - 排队深度/等待时长时间曲线（容量规划依据）
- **开放查询 API**：让企业 IT/财务系统拉数据对账——
  能被集成比自己报表好看更重要。

## 不采用

- 账单与用量分开记两套（必然对不上）。
- ~~agent 上报即入账、无本地 WAL（断网丢数据）~~ → 修正（2026-10-12）：
  agent 无状态是更高优先级决策，断网期间有界内存缓冲 + gap 标记；
  数据洞在私有部署可信环境下可接受，对账按 gap 区间标记处理。
  若未来运营跨组织算力池再评估追加溢出文件。
- 首版做防篡改计量（私有部署可信；若未来运营算力池再补交叉验证）。
